搭博客时最先要决定的不是用什么主题，而是**内容怎么变成 HTML**。这一步选错了，后面换主题、加功能都只是补救。

目前的方案很简单：Markdown 写文件 → 构建时生成 HTML → 扔到静态托管。没有数据库，没有 Node 服务常驻，也没有后台登录。

## 三种渲染方式

大致可以这么分：

| 方式 | 何时生成 HTML | 首屏 | 运营成本 |
| --- | --- | --- | --- |
| 服务端渲染 SSR | 每次请求 | 依赖服务器 | 需要跑进程 |
| 静态生成 SSG | 构建时一次 | 最快，可上 CDN | 几乎没有 |
| 客户端渲染 CSR | 浏览器里 | 慢，白屏风险 | 几乎没有 |

博客的内容特征是**读多写少**：写完一篇文章，可能几个月都不改一次。这种场景下，每次请求都重新渲染一遍纯属浪费。用 SSG 生成一次，之后所有访问都命中 CDN 缓存，首屏时间只跟网络延迟有关。

## 具体到这套配置

构建流程里真正干活的就是几行配置：

```ts
// src/content.config.ts
const blog = defineCollection({
  loader: glob({ pattern: '**/*.md', base: './src/content/blog' }),
  schema: z.object({
    title: z.string(),
    pubDate: z.coerce.date(),
    tags: z.array(z.string()).default([]),
    draft: z.boolean().default(false),
  }),
});
```

schema 的作用经常被低估。它保证每篇文章的 frontmatter 是合法的：日期能解析、标签一定是数组、`draft` 一定是布尔值。写错字段时构建直接报错，而不是在页面上渲染出一个 `Invalid Date`。**把错误提前到构建期，是静态站最大的好处之一。**

## 什么时候这套方案会不够用

也不是没有代价，以下几点比较现实：

1. **需要实时数据**：评论、点赞、阅读量。静态站自己做不到，得挂第三方服务或者开一个小 API。
2. **内容量极大**：几万篇以上时，每次全量构建会变慢，需要增量构建或者按需渲染。
3. **多人协作**：没有后台，编辑就得会 Git 和 Markdown。团队里有非技术成员时这是硬门槛。

对我这种一个人写、想改哪里改哪里的场景，这三条都不成立。

## 一个容易被忽略的细节

静态站还有个隐性好处：**内容是可迁移的**。

构建产物是一堆 HTML 文件，源文件是一堆 Markdown，两者都不绑定任何平台。今天放 GitHub Pages，明天换 Cloudflare，复制一下目录就行；哪天想换框架，Markdown 原样拿走去 Hugo 或者 Next.js 也不会丢。

> 技术选型里，能低成本退出的方案，往往比功能更多的方案更值得选。

这也是我最终没选带后台的 CMS 的原因——它确实更方便，但它把内容和平台绑在了一起。

## 小结

静态站不是万能解，但对"个人写、低频更新、读多写少"的博客来说，它的匹配度最高：速度快、成本近零、内容可迁移。需要动态能力时再局部加，而不是一开始就上全套。
